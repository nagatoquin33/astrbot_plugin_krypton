# 氪 · Krypton

当前版本：`v0.4.0` · [更新记录](CHANGELOG.md)

查询 AstrBot 已知会话的真实 ID，按需读取目标近期消息，增强原生主动型能力中的跨会话未来任务，并提供可选的 JEV 群聊参与判断。独立插件，共用 AstrBot 的任务数据库、调度器和任务唤醒 Agent。

## 安装与启用

在 AstrBot 插件管理中通过仓库地址安装：`https://github.com/nagatoquin33/astrbot_plugin_krypton`。

将本目录放到 AstrBot 的 `data/plugins/astrbot_plugin_krypton` 并重载插件。使用 AstrBot 已包含的依赖，包括可选 JEV 请求所需的 aiohttp。面向 AstrBot 4.29 系列，使用原生 Agent Runner；本地验证版本为 `4.29.0-beta.2`。

在当前聊天使用的配置中打开 **AI → 能力 → 主动型能力 → 启用**。插件的未来任务扩展服从这个原生开关；关闭后不会向普通聊天请求提供增强任务工具，直接调用也会被拒绝。会话查询不受任务开关影响。

模型需要支持工具调用。如果人设有工具白名单，请允许 `list_chat_sessions`、`get_chat_context`、`get_group_activity` 和 `future_task_plus`。任务需要搜索、文件操作、业务系统时，仍需配置对应工具、插件或 MCP。

## 主动能力的实现范围

自主安排由当前主对话模型根据工具说明和会话上下文判断：它可以因自己的承诺、未完成事项或值得跟进的变化而调用任务工具，不要求用户先说“创建提醒”。模型决定安排后，由原生调度器持久化，到点唤醒原生 Agent 执行。

插件不会额外启动后台规划模型，不会修改系统提示词、用户输入或会话历史，也不会向任务指令附加固定行为规则。工具本身的说明会解释可用动作、自主安排的用途与执行参数。是否在某段对话中主动建任务仍取决于当前模型的判断，不保证每次提到未来事项都会建立任务。

普通请求中，仅当增强工具已启用且原生开关开启时，插件才从本次工具列表移除基础 `future_task`，保留增强入口，避免两个相似工具让模型混淆；不修改全局原生工具。定时任务唤醒路径可能同时出现基础与增强工具，增强工具的调用同样检查原生开关。

## 可选 JEV 群聊参与判断

默认关闭。在插件配置中开启“启用 JEV 群聊参与判断”，填写 TypeSafe API Key，并在“允许主动接话的群会话”中填写完整群 UMO，例如 `qq:GroupMessage:123`。平台 ID 应使用实际 `/sid` 或会话查询结果中的值；空列表不启用任何群。当前会话也需要开启 AI 和原生主动型能力。

当白名单群收到普通消息时，JEV 判断现在是否值得主 Agent 参与，分数达到阈值（默认 0.75）后，这条消息通过原生流程交给当前群的主 Agent，继续使用该群模型、人设、工具与权限。JEV 本身不生成回复或执行工具，不提升消息发送者的管理员权限，也不筛选 @、指令或已有未来任务。关闭 JEV 后仍可由主模型自行安排未来任务。

`typesafe_model_id` 默认及留空时使用 `jev-latest`。API 地址接受根地址、`/v1` 或完整 `/v1/systemone`；HTTP 请求遵守环境代理和 `no_proxy`。配置的参与偏好可说明感兴趣的话题和熟悉的称呼，提供给判断层作为参考。

检查由新消息触发，没有后台轮询。同一物理群默认至少间隔 30 秒判断一次，唤醒或正常回复后默认冷却 300 秒；可在配置中调整。OneBot 基础群 UMO 覆盖该群的隔离会话，填写成员前缀的完整 UMO 则只匹配该会话；同群共享请求间隔和冷却，近期消息缓冲按完整 UMO 隔离。

开启后，会把当前消息及本进程近期最多 10 条、每条最多 1000 字符的消息文本/类型占位与昵称发送给配置的判断服务。缓冲、检查间隔和冷却保存在内存中，重载后重置。图片、语音等仅提供类型占位。缺少 Key、服务超时、限流或返回格式异常时跳过本次主动接话；不会据此触发另一轮主模型请求。正常聊天和原生未来任务不受判断结果影响。

## 工具

| 工具 | 用途 |
| --- | --- |
| `list_chat_sessions` | 按群名、昵称、备注或会话 ID 查询，返回完整 `session`，支持分页。 |
| `get_chat_context` | 按需读取指定会话近期消息，每条只返回发言人、时间和正文；本地回退时附简短说明。 |
| `get_group_activity` | 比较已知群自管理员上次查看群内容以来的新消息数，方便选择需要了解的群。 |
| `future_task_plus` | 创建、查询、查看详情、修改、暂停、恢复和删除原生 Agent 任务，支持跨会话目标与必要背景。 |

发送消息继续使用原生 `send_message_to_user`。跨会话联系前，查询目标并把完整 `session` 原样传给发送工具或任务工具；不要猜 ID，重名时需要确认目标。

会话列表来源仍是 AstrBot 已保存的会话记录和名称/备注，不枚举平台群/好友列表。查询只展示已加载且声明支持主动消息的平台。平台支持不代表某个用户、群或消息格式一定可达，最终以实际发送结果为准。

列表每行只保留完整 `session`、有效名称 `name`，以及仅当前会话出现的 `is_current=true`。重复的原始名称、平台/类型拆分字段和 `is_current=false` 不再返回。昵称中的双向控制符、伪空白等会清理，正常文字和 emoji 保留；只是重复会话 ID 的名称会省略，无名会话仍可按 ID 搜索。当前会话与有名称的会话优先展示，分页数量和总数仍覆盖全部有效目标。

## 目标近期消息

`get_chat_context(session, limit=10)` 最多返回 20 条消息，按时间先后排列。查询目标平台和原会话 UMO，不把来源会话的历史搬到目标。

- OneBot（AstrBot 的 `aiocqhttp` 适配器）优先调用 `get_group_msg_history` 或 `get_friend_msg_history`，具体支持情况取决于 NapCat 等协议实现。调用有 8 秒超时，复用 AstrBot 已连接的适配器，不另配凭据。
- 平台不支持、调用失败或超时时，尝试通过原生 `PlatformMessageHistory` 读取本地消息，不用 `ConversationV2` 的 LLM 对话替代现场发言。群聊的本地回退遵守目标会话的 `group_message_history_enable` 设置。
- 正常结果仅包含 `messages`，每条只保留 `sender`、`time`、`text`。不返回会话、消息或发言人 ID、角色权限、逐条截断标记及重复查询时间。时间按调用会话配置的时区显示为 `月-日 时:分`，跨年份保留年份。
- 本地回退附一句“仅本地留存记录，可能不完整”，查询失败返回简短错误；详细原因写入日志。空结果不能说明聊天里没人发言。平台成功返回空列表时不拿过时本地记录填充。
- 发言人名称会清理控制字符；消息中的提及优先显示本批记录中已知的昵称，未知对象显示 `@某人`，不改动正文中的普通数字。超过 2000 字符的正文以省略号结束。
- 图片、语音、视频、文件等只返回类型占位，不下载媒体，也不生成图片或语音内容描述。
- 普通成员只能读取当前会话，跨会话读取仅限管理员；鉴权在平台或数据库查询之前完成。聊天内容和名称作为数据处理，不是执行指令。

群聊隔离模式的 UMO 可能带成员前缀。OneBot 在线历史查询按原生发送规则提取真实群号；本地回退严格按原 UMO 查询，不把同群其他成员的独立上下文合并进来。

## 群活动与主动联系

模型可以在聊天中通过 `future_task_plus` 自主安排后续行动，到期由原生 Agent 根据会话和任务内容决定是否联系、聊什么以及调用哪些工具。私聊长期没有回应时，模型可以查询群状态，再选择查看某个群的现场；群活跃并不表示特定成员在线。插件不设置固定心跳，首次及后续任务均由模型决定创建，模型也可能选择不创建或不发送。

管理员成功通过 `get_chat_context` 查看 OneBot 群聊的非空在线历史后，插件按管理员和完整会话保存最新消息基准。`get_group_activity` 查询已知群并统计基准之后的平台消息，查询状态本身不改变基准。首次尚未查看、平台接口失败、历史为空或基准不在最近返回的最多 100 条消息中时增量显示未知；本地回退不会更新在线基准。重启后基准保留，群消息内容不会由此功能另存。跨会话查询仍仅限管理员。

即使没有基准，群状态也会返回最近 `hours` 小时（默认 24，范围 1–168）内的平台**可见**消息数，帮助比较活跃度。它只统计平台返回的最近最多 100 条有时间的记录，可能偏少，群活跃也不表示特定成员在线。结果优先展示有新增消息的群，增量未知时参考近期可见数量，已看完的群随后，不可用的群最后；排序后再分页。每次查询会读取所有已知群，同平台同物理群只查询一次历史，隔离会话仍按自己的基准分别计算。群多时耗时和平台请求数随之增加。翻页期间若消息变化，排序也可能改变。

## 未来任务操作

- `create`：一次性任务传未来的 ISO 时间 `run_at`，自动推断单次执行；周期任务传五段 `cron_expression`，如 `0 8 * * mon-fri`。
- `list`：默认展示投递地或创建来源在当前聊天的可管理任务。管理员可传 `scope="all"` 查所有 Agent 任务，也可用 `session` 筛选目标。
- `get`：查看完整指令、背景、目标、时区、实时下次执行时间、最近执行时间、状态和错误。
- `edit`：修改名称、指令、背景、目标、时区或日程，只传要改的字段。新 `run_at` 或 `cron_expression` 可以切换计划类型。
- `pause` / `resume`：暂停或恢复原任务。过期的一次性任务需要先修改为未来时间。
- `delete`：删除任务。

`note` 是实际任务指令，可写清目标、完成或停止条件和通知条件。`background` 描述来源会话发生了什么、为什么联系目标，以及希望交流或行动的方向；避免只写“刚才那件事”。名称避开了 AstrBot 调用上下文的保留参数 `context`。

跨会话创建时仍直接指定 `session`，由原生 Agent 在目标会话执行。任务数据会附上来源 UMO 和模型提供的背景，不额外加入固定行为规则。创建时的背景不是实时动态；目标 Agent 可在执行时调用 `get_chat_context` 查看近期消息，再决定如何行动、是否发言。插件不强制调用，不自动注入现场，也不增加独立 `session_send` 或规划模型。

任务保存于原生数据库，重启后可恢复，也可以在原生未来任务页面管理。关闭能力开关或卸载插件不会自动删除已经建立的原生任务；如需停止任务，先暂停或删除。

一次性任务执行后由 AstrBot 删除，包括执行失败的情况，之后需要查原生日志。周期任务可查询上次错误。执行成功和消息投递成功是不同结果，只有发送工具返回成功才能认为已投递。

## 权限

会话列表查询和跨会话操作仅限当前配置中的 AstrBot 管理员。普通成员可读取当前会话近期消息，在当前聊天创建任务，并管理自己创建的任务。管理员可管理 WebUI 创建的 Agent 任务；插件不操作其他插件的 `basic` 维护任务。原生发送工具仍执行自身权限检查。

## 升级说明

早期目录名是 `astrbot_plugin_session_tasks`，现为 `astrbot_plugin_krypton`。先停用旧插件再安装当前目录，避免同时注册相同工具。原生任务记录保留，旧版 `session_tasks` 元数据及其中的背景可以继续读取，修改后使用 `krypton` 元数据。

`v0.2.1` 移除了 `v0.2.0` 的额外后台规划、独立规划配置和提示注入，统一服从原生主动型能力开关。早期规划产生的原生任务不会自动删除，可以通过工具或原生页面管理。

`v0.3.0` 增加按需目标近期消息查询，并完善原生跨会话任务的来源与背景描述。会话列表保持本地查询，不扩展无本地记录的群/好友发现。

`v0.3.1` 精简会话列表回包并清理展示名，优先展示当前会话与有效名称，保留无名会话的 ID 检索和分页。

`v0.3.2` 精简近期消息回包，每条只保留发言人、当地时间和正文，清理昵称控制字符并用名称替代提及中的 ID；本地回退和失败只附简短说明，详细原因写入日志。

`v0.4.0` 增加群活动查询和可选 JEV 群聊参与判断。有新增消息的群优先展示，同平台同物理群复用一次历史请求；JEV 默认关闭，仅筛选白名单群普通消息的参与时机，具体回复与工具调用交给原生主 Agent。@、指令及已有未来任务保持原有执行流程。

## 开发验证

在具备 AstrBot、pytest、pytest-asyncio 和 Ruff 的 Python 3.12+ 环境运行：

```powershell
python -m pytest -q
python -m ruff check .
python -m ruff format --check .
```

测试默认读取相邻 `AstrBot` 源码，也可用 `ASTRBOT_SOURCE` 指定源码；没有源码时使用安装环境中的 AstrBot。数据库在临时目录中创建，使用真实 SQLite 和 APScheduler，平台传输和模型唤醒由测试接收端代替，不向真实用户发送消息。

测试覆盖会话查询不枚举平台目录、跨会话任务携带来源与背景、唤醒后读取目标新消息并投递到目标、历史来源与失败降级、隔离作用域、权限、任务管理、重启加载和提示内容不变。平台接口和任务执行者使用测试替身，真实模型是否主动查现场、如何判断与线上投递效果，仍需接入所用模型验证。

插件复用原生内部 `_build_trigger` 校验器，避免无效日程先写入数据库；升级 AstrBot 后需要重新验证该接口。
